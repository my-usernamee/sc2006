## End-to-end use-case paths

**Create report → automatic matching:** `ReportForm`/`MapPicker` → report API → validation/location proof/upload → report service → serializable transaction → matching service → pure `calculateMatchScore` → MatchResult and Notification → owner notification → protected match detail with score.

**Submit/review claim:** `FoundReportDetailPage` → claim API → claim service transaction → ownership/status/Pending checks → OwnershipClaim + Finder notification → `ClaimDetailPage` → Finder decision transaction → both report statuses + owner notification → Approved-only contact DTO.

## Explicit implementation choices

One Pending claim per report prevents competing handovers. Rejection unlocks both reports, allowing another claim. Soft deletion removes a report from application availability while preserving existing claim history. These policies should be reflected in the final design description. Persistence is Prisma/PostgreSQL; `PersistentStore<T>` in the conceptual diagram maps to Prisma delegates rather than a fabricated extra collection layer. Native TypeScript arrays represent `List<T>`.
